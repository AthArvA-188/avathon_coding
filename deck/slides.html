The brief

Three questions, one runnable system

  • 1. Demand: what do the next 4 quarters look like, per SKU × geo × channel × week?
  • 2. Supply: what MPS and weekly pack-out plan supports that demand inside the real constraints — 17,280 u/week, 224,000 u/quarter, only 4 variants packed out per week, WOS targets of 12 (supply) and 13 (channel)?
  • 3. Disruption: what changes when V2 and V4's shared enclosure is capped at 4,500 u/week for the first six weeks of next quarter?

Everything below can be reproduced with one command from the raw xlsx, and every headline number is re-checked by an independent audit script and 54 automated tests.

Forecast · approach

One global model, honest baselines, explicit holidays

  • Model: XGBoost quantile regression (P10/P50/P90) — one global model across all 124 series, recursing week-by-week over the 52-week horizon. Holiday weeks are explicit features, not left to be inferred.
  • Trained on log(units) — series scales span four orders of magnitude, and quantiles survive the transform exactly — with rows weighted by volume so the loss cares about business-relevant weeks.
  • What we tried and dropped (all scored on the same 13 hidden weeks): raw-scale target 53% WAPE → log 41% (but −30% bias) → mean-model recursion diverged → volume weights: 37.6% WAPE, +3.3% bias — kept.
  • Known-ahead prices: the pricing file extends into the horizon; future promo prices are legitimate features.

Forecast · lifecycle

Launches, sell-outs and volume caps are first-class

  • V10 & V11 launch inside the horizon with zero history. They ramp on the launch curves of the earlier exclusives (V8/V9), deseasonalized and re-shaped to FY2024's holiday calendar, scaled to exactly their committed volumes: 57,407 and 23,689 units.
  • One-time deals exhaust on schedule: V5 sells out 2023W51, V7 by 2024W10, V6 by 2024W21 — cumulative forecast never exceeds remaining volume, enforced and tested.
  • Interpretation call (flagged to client): the stated "lifetime volumes" for exclusives cannot be lifetime — V8 has already sold 2.4× its number — so they are read as forward volumes from the last actual week. One-time-deal numbers do behave as lifetime totals.
  • V12 (sold out 2022W14) forecasts zero.
Supply plan · formulation

An optimizer plans; an independent validator checks

Decisions (mixed-integer program, CBC, ~30 s): weekly production per variant, which ≤4 variants use the pack-out slots, and shipments per geo across each geo's freight frontier.

  • Hard: 17,280 u/wk · 224,000 u/qtr · slot limit · inventory balances · volume caps · no shipment that can't land in-horizon.
  • Soft, in strict priority: unmet demand ≫ channel WOS (13) > supply WOS (12) > freight cost > holding.
  • WOS is measured run-out style — weeks of forward demand covered — which matters when Black Friday burns stock 10× faster.

Never trust the solver: after every solve, 9 independent checks re-verify each rule from the stored plan — including replaying all inventory math from the shipment records. The pipeline refuses to report success otherwise.

9/9 validators PASS

Two adversarial review rounds (with mutation testing) hardened this: they proved a do-nothing plan passed the original checks, found a phantom-shipment exploit and a missing freight mode — all fixed before the results you're reading.

And a second method keeps it honest: a transparent greedy heuristic (the plan a human would build by hand) runs through the same validators. It's cheaper ($4.62M freight) and holds fatter buffers — but leaves 99,455 units unmet vs the MILP's zero. Cross-week lookahead is worth real money in a capacity-starved year; that's the measured reason the optimizer ships as primary.

Shortage scenario · setup

4,500 units a week, split by stockout risk — not by rule of thumb

  • V2 + V4 share an enclosure; combined production ≤ 4,500 u/wk for 2023W40–W45 (Jul–Aug, the pre-holiday build window).
  • Allocation rule: we don't hand-pick a split. The same optimizer allocates scarce units to whichever variant is closer to running out (the WOS-equalizing objective) — auditable and repeatable.
  • What it chose: alternating full-cap weeks — batching preserves the scarce pack-out slots — landing on an exact 50/50 split (13,500 u each).

Where this stack goes · 1 of 3

Foundation forecasting models: use them where history is thin

  • Reach for TimeGPT / Chronos / TimesFM where this problem is weakest: zero-history NPIs (V10/V11 — today an analog heuristic), sparse tail geos (G3/G5), short-history exclusives. Zero-shot models encode cross-domain launch and sparse-demand priors we can't learn from one product's history.
  • Keep the task-specific model where it wins: promo-heavy weeks on a client-specific fiscal calendar with known-ahead prices — features a zero-shot model can't see. Our XGBoost's edge is exactly the holiday weeks.
  • Failure mode to watch: calendar misalignment — these models learned Gregorian seasonality; our weeks are fiscal and promos move. Score before trusting.
  • The harness already exists: the same 13-week holdout scorer that judges XGBoost vs seasonal-naive would score any foundation model head-to-head in an afternoon.
Where this stack goes · 2 of 3

LLM signals and agentic loops — mapped onto this exact codebase

LLM-augmented signals. The V2+V4 scenario arrived as prose; in production it arrives as a supplier email. An LLM extracts structured events — (variants, weeks, cap) — into the same scenario hook the optimizer already consumes. Auditability: every extracted event keeps its source link, prompts are versioned, planner overrides are logged, and an eval harness gates any change that would touch forecast weights.

Agentic decomposition — already half-built:

  • Forecaster agent = forecast.py (authority ends at the demand table)
  • Planner agent = mps.py (proposes, never self-certifies)
  • Verifier agent = validate.py — independent today, by design
  • Scenario agent = scenario.py (re-plans under disruption)

Handoffs are typed tables in SQLite; a verifier rejection bounces the plan back with the violated constraint attached; humans own assumption changes (the D-decision log) and disruption acceptance.
